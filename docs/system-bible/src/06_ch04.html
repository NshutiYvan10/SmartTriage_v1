Registration & Patient Identity

Identity is where patient safety begins: the wrong record attached to the wrong person poisons everything downstream. SmartTriage identifies people with deterministic keys only — a national ID and/or an RFID card — and refuses to guess.

In this chapter
  • Registering a patient (and every validation)
  • MRN and visit-number formats
  • Duplicate detection
  • The shared cross-hospital identity (PersonIdentity)
  • Unknown patients: placeholders, resolution, merging
  • Allergies & chronic conditions

4.1Who can register

SUPER_ADMIN HOSPITAL_ADMIN REGISTRAR NURSE DOCTOR can register patients — with one twist: today's triage nurse cannot (the triage station must stay focused on triage, and separation of duties keeps one person from both creating and triaging a record). Registration is pinned to the caller's own hospital; only SUPER_ADMIN may register elsewhere.

4.2Registering a patient, step by step

Capture demographics.

Required: first name, last name, hospital. Everything else is optional: date of birth, gender, national ID, passport, birth certificate, phone, the 5-level Rwanda address (province→village — any subset; an unresolvable location ID is silently dropped, never blocks registration), emergency contact, guardian details (for children), blood type, weight, free-text allergies/conditions, pregnancy status.

Blank means absent.

Empty strings are converted to null before saving, so the database's uniqueness rules (which ignore nulls) treat “left blank” correctly — two patients without passports are not “duplicates of each other”.

Duplicate check.

The three Tier-1 identifiers — national ID, passport, birth certificate — are each checked against active patients at this hospital. A match refuses registration with a “duplicate patient” error naming the conflicting field. (The database enforces the same rule with unique indexes as a backstop.)

MRN allocation.

The Medical Record Number is {hospitalCode}-{sequence} (e.g. KFH-1024), drawn from a durable per-hospital database counter — it survives restarts and concurrent registrations. Up to 10 collision-skip attempts, then the registration fails loudly rather than issuing a duplicate MRN.

Shared identity link.

If a national ID and/or RFID card was captured, the patient is linked to (or creates) a cross-hospital PersonIdentity (§4.4). No ID and no card → the record stays purely local.

Structured history.

Each allergy/condition entered at the desk becomes a structured row (allergy defaults: severity UNKNOWN, verification PATIENT_REPORTED; condition default status ACTIVE). Each row is best-effort: a malformed entry is logged and skipped, never blocking the registration itself.

Optionally open the visit.

POST /patients/register creates the patient and their visit in one transaction (the normal front-desk flow); POST /patients creates the person only. Visit numbers are V-{hospitalCode}-{yyyyMMdd}-{00001…} from their own durable per-day counter.

Business rule

One patient may hold only one open visit per hospital. Registering a returning patient who already has an open visit refuses the second visit (“already has an open visit”) — the correct move is to find the existing encounter.

4.4The shared identity: PersonIdentity

One PersonIdentity row represents one human being across all hospitals. Each hospital still keeps its own local Patient record; the identity links them. It is anchored by up to two keys:

  • National ID — the civil identity;
  • RFID card UID — a physical card, which makes identity work even for people without an ID (newborns, foreigners, unconscious unknowns).

Matching is deterministic-exact only. There is no fuzzy or probabilistic matching anywhere — a wrong merge would attach one person's allergies to another and is treated as a patient-safety incident by design. The resolve rules:

A registration arrives with national ID and/or card. What happens?
Neither key given — no shared identity; the patient stays local.
Keys are new — a new PersonIdentity is created (concurrent duplicates resolved by re-reading the winner).
One key matches, the other is new & unused — the new key is attached (e.g. issuing a card to a known person, or an ID arriving for a card-anchored unknown).
Both match the same identity — that identity is used.
Keys point to different identities, or conflict with what's on file — rejected with an identity-conflict error (“…already belong to different patients — reconcile manually”). The system never auto-merges people.
Note

Swapping a lost/damaged card is a separate, explicit, audited action (replace card). It refuses a card that already belongs to someone else, and returns the old card UID for the audit trail.

What the shared identity unlocks — the always-available safety summary and the consent-gated deep record — is covered in §14.

4.5Changing demographics later

  • Demographic correction (admin/registrar/nurse/doctor): partial update; changing the national ID re-runs duplicate detection against other active patients at the hospital, then re-links the shared identity (keeping the existing card anchor).
  • Pregnancy status (NURSE/DOCTOR only — it drives medication safety): one of PREGNANT · POSSIBLY_PREGNANT · BREASTFEEDING · NOT_PREGNANT · NOT_APPLICABLE · UNKNOWN, with optional gestational age. Transitioning into a pregnant state automatically re-screens up to 10 of the patient's active visits for teratogenic medications already prescribed (§8.4).
  • Allergies / chronic conditions (nurse/doctor): both the free-text quick fields and the structured rows (§4.7).

4.6Unknown patients: placeholders → identification → merge

An unconscious arrival can't wait for paperwork. The system creates a placeholder: first name “Unknown”, a NATO-phonetic label (“Alpha”, “Bravo-2”…), flagged isUnidentified. Care proceeds normally. Later, identity is resolved one of two ways:

Who is this person really?
A new person — rename in place: real name (and/or card, national ID) is written onto the same record; the UUID never changes, so every downstream order and note stays valid. Requires a name or a card; a card belonging to someone else is refused and routed to the merge path. The placeholder label is kept for audit.
An existing patient — merge: all visits, allergies, conditions and clinical-sign events are re-pointed to the real record (in batches); the placeholder is soft-deleted with its identification stamp preserved. Guards: same hospital only, not into itself, and two different shared identities are never merged (fail-closed).
Still unknown — an IDENTITY_UNRESOLVED alert keeps the registrar chasing it (escalating if ignored).
