Devices: Bedside Monitor, Gateway & RFID Desk

Three pieces of hardware extend SmartTriage past the keyboard: the ESP32-S3 bedside monitor, the Raspberry Pi gateway, and the RFID registration reader. This chapter covers their user-visible behavior and operating rules — not electronics.

17.1The bedside monitor

Measures seven vitals: heart rate (ECG-derived, pulse-ox fallback), SpO2 + perfusion index, respiratory rate (ECG-derived), systolic/diastolic blood pressure (oscillometric cuff), and temperature (contact sensor). A five-page touch UI: dashboard tiles · live ECG+pleth waveforms · 10-minute trends · guided BP measurement · device status. Vitals transmit to the backend every 5 s with the device API key; an offline ring buffers ~5 minutes and flushes on reconnect.

Honesty rules (clinical trust)

  • Unmeasured values show “--”; an absent or non-delivering sensor states it in words (“SpO2 sensor not detected”, “place finger on sensor”); a disconnected stream freezes visibly stale rather than pretending to be live.
  • Weak ECG signal dims the number and shows “ECG — weak signal, check electrodes”; heart-rate display moves only when the rhythm truly changes (beat-validation logic).
  • Simulation mode shows a permanent amber banner and never transmits — demo data cannot reach a clinical record.

Blood pressure

  • Guided oscillometric measurement with a hard safety envelope: pressure-feedback inflation, hard abort at 200 mmHg, every error path vents the cuff, on-screen cancel (press-and-hold during measurement).
  • CAL PUMP is the on-device calibration: it measures the pressure scale on the real cuff and stores it in device flash; the scale was validated against a reference monitor. Operational rules: fully empty the cuff before each measurement; the current sensor board cannot read above ≈115 mmHg, so markedly hypertensive readings saturate (a documented hardware limit — prototype-grade, fine for normotensive demo subjects).

17.2Device registry & identity

  • Admins register devices (type, serial, bed binding). The API key is displayed once; regenerating invalidates the old key instantly. Ingest requires key + matching serial.
  • Paramedics may self-register a personal transport monitor (owned by them, pinned to their hospital) and pull its live telemetry into an EMS run.
  • Device statuses: registered → online/monitoring ⇄ offline · error · decommissioned; heartbeats every few seconds, disconnect handling per §7.2.

17.3The gateway & simulators

  • The Pi is the ward's single point of egress: real monitor traffic passes through unmodified.
  • Its demo console can run three simulator families (bedside vitals, triage-style presentations, paramedic transport) — each registered as its own clearly-named device so simulated streams are always attributable and separable from real ones.

17.4The RFID desk

  • Tap → the reader sends the card UID → the registrar screen resolves the person (§4.4) and opens the register/arrive flow. Unknown cards offer enrollment (attach to a person); conflicting cards refuse with the identity-conflict rule.
  • Card operations that change identity anchors (issue, replace) are explicit, audited actions.

17.5Demo-day runbook

Tip — the checklist
  • Backend: simulation flag off; devices provisioned with real API keys.
  • Monitor: fresh batteries morning-of (the pump browns out on weak cells); cuff fully empty before each BP; calibrate touch once on-site; expect the boot recap line on serial if diagnosing.
  • Network: monitor → gateway → backend on the venue WiFi; verify one end-to-end vital appears on the patient chart before the audience arrives.

The rules that apply everywhere: how errors are shaped, how records are scoped and soft-deleted, what happens offline, and how the system behaves under concurrency.

18.1The error model

CodeMeaningTypical example
400Invalid input (schema/validation)Missing required field, malformed value — checked before permissions, so a permission probe with a bad body sees 400, not 403
401Not authenticatedExpired token (15 min), bad device API key
403Authenticated but not allowedNurse calling a prescribe endpoint
404Not found — or not yoursRecord from another hospital (existence not confirmed)
409Conflict / duplicateDuplicate patient identifier, duplicate bed code
422Business-rule refusalDischarge without summary; withdraw a non-given consent; triage a non-awaiting visit

All responses share one envelope (success flag, message, data). Business-rule messages are written for humans and are quoted throughout this document.

18.2Soft delete & hospital scoping

  • Every entity carries isActive; deletion flips it; every read filters on it. Uniqueness rules are “partial” — they apply only among active rows, so a deactivated record frees its identifiers (e.g. a cancelled invitation frees the email).
  • Nearly every query is hospital-scoped at the repository level; the deliberate exceptions are listed in §1.3.

18.3Offline sync

  • Clients may submit batches of offline-created records (CREATE/UPDATE with JSON payloads). Each record lands as synced / conflict / failed; a failed record never aborts the batch. Admins can resolve conflicts (accept server / accept client / merge) and monitor per-hospital sync status. READ_ONLY users cannot sync.
Needs clarification

The offline conflict detector is currently a conservative stub (it never flags version conflicts), and conflict “resolution” relabels the sync record without visibly re-applying data to the target entity. Before relying on offline mode in production, the team should decide the real conflict policy and implement the re-apply path. (Also listed in Appendix C.)

18.4Concurrency & idempotency

  • Durable counters (MRN, visit numbers) serialize allocation in the database — restart-proof, collision-checked.
  • Partial-unique indexes backstop the big invariants: one bed per patient, one active visit per bed, one effective consent grant, one shift-lead per shift, one active template per period.
  • Post-commit publishing: WebSocket events and governance notifications fire only after the transaction commits — a rolled-back save can never announce itself.
  • Idempotent writes where double-submits are likely (allergies, transfers, alert dedup, EMS acknowledgments).

18.5Time & localization

  • Operational logic (shifts, schedulers) runs on Africa/Kigali; timestamps are stored UTC; device readings carry NTP-synced capture times.
  • Rwanda's 5-level administrative hierarchy (province → village) is built-in reference data for addresses; the mains-frequency and language defaults are Rwanda-appropriate.
