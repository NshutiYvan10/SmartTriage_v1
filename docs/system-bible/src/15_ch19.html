FAQ, Common Mistakes & Best Practices

The questions every new teammate asks, the mistakes everyone makes once, and the habits that keep the system trustworthy.

19.1Frequently asked questions

“Why can't this nurse prescribe / order a lab?”

By design — the ratified capability matrix (§2.3) makes prescribing and ordering doctor-only, enforced server-side. The nurse's medication tab is an administration view, not a lesser bug.

“Why does the doctor see an empty patient list?”

They're off-shift, or their shift doesn't cover the zone. Patient lists derive from the roster (§2.5). Charge-nurse/lead authority sees everything.

“Why did the patient's triage change by itself?”

Dynamic re-triage (§5.7): a worsening clinical sign or sustained critical vitals auto-escalated the category. The record is labeled system-triggered with its cause. The system never de-escalates on its own.

“Why is this record 404 when I know it exists?”

It belongs to another hospital (or is soft-deleted). Cross-hospital access has exactly two doors: the safety summary (always) and the consented/break-glass deep record (§14).

“Why can't I acknowledge this critical alert?”

Critical acknowledgments require a written reason — the empty note is the blocker (§15.4).

“Why won't discharge save?”

No discharge-summary document yet (§6.6). Write it first; the gate is server-side.

“Can we delete this mistaken record?”

No — soft delete + supersession is the model. Notes/documents are corrected by superseding; diagnoses by amending; wrong dispositions by a new visit. History is never rewritten (§18.2, §15.1).

“The monitor shows -- for a vital.”

That's the honesty rule (§17.1): unmeasured means unshown. Check sensor contact; the device status page and serial recap say exactly which sensors are alive.

Treating the UI as the security boundaryHidden buttons are courtesy; every rule is re-checked server-side. Test authorization with API probes, not screenshots

Editing a note in place (developers)Notes are immutable; build on supersession. Same for audit rows (DB trigger will refuse)

Trusting client-sent identity fields (developers)Actor identity is always resolved server-side; client-supplied names are display hints at best

19.3Best practices

  • Clinical users: acknowledge with substance (the note is the record); keep the roster current — everything routes off it; resolve placeholders quickly (unidentified patients age poorly).
  • Admins: review the override register and break-glass feed on a rhythm, not on scandal; keep at least two charge nurses; deactivate rather than delete.
  • Developers: preserve the eight principles of §1.4 in every change; add new safety gates with the same trio (server-enforced, override-with-reason, register entry); write migrations additively; when a save should trigger automation, make the automation best-effort after commit.
  • Testers: probe with schema-valid bodies (validation fires before authorization, §18.1); use throwaway users via the admin API — never repurpose real accounts; remember soft-deleted fixtures still occupy unique keys only while active.
